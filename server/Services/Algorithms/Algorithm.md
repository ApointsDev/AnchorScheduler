# 智能调度算法文档

本文档详细阐述了 TimeManager 系统中用于个人任务调度和团队任务调度的核心算法流程。

## 1. 个人任务调度 (Personal Schedule)

个人任务调度的目标是在满足所有硬性约束（如固定会议、截止日期、依赖关系）的前提下，为灵活任务（DDL型任务）自动分配具体的时间段。

### 核心流程

整个调度过程由 \AlgorithmService.scheduleTasks\ 方法编排，主要包含以下步骤：

#### 1.1 任务解析与分类 (Task Parsing)
系统首先接收原始的任务列表，并根据任务属性将其分类为两类：
*   **固定事件 (Fixed Events)**: 
    *   用户明确指定了 \isFixed: true\ 的任务。
    *   或者 \isFixed\ 未定义（默认视为固定）。
    *   或者任务具有明确的开始和结束时间且没有估计时长（Duration）。
    *   这些任务在调度中被视为**不可移动的障碍物**。
*   **灵活任务 (DDL Tasks)**: 
    *   用户明确指定 \isFixed: false\。
    *   或者任务具有估计时长（Duration）。
    *   这些任务是**需要被调度**的对象。
    *   **最早开始时间 (Earliest Start)**: 默认为任务的 \startTime\（如果未指定则为当前时间）。
    *   **截止时间 (Deadline)**: 默认为任务的 \ndTime\（如果定义了区间）或 \dueDate\。

#### 1.2 时间槽生成 (Time Slot Generation)
系统根据配置（如每日工作时间 8:00-22:00，时间槽粒度 60分钟）生成可用的时间槽池。
*   时间范围：从当前时间开始，延伸至所有灵活任务中最晚的截止日期。
*   每个时间槽代表一个潜在的任务执行单元。
*   **预处理**: 系统会预先剔除被“固定事件”占用的时间槽。

#### 1.3 依赖分析 (Dependency Analysis - Topological Sort)
如果任务之间存在依赖关系（例如 任务A 必须在 任务B 之前完成），系统使用 **拓扑排序 (Topological Sort)** 算法对任务进行排序。
*   **目的**: 确定任务的调度优先级顺序。
*   **校验**: 检测是否存在循环依赖（Cycle Detection），如果存在则抛出错误。

#### 1.4 冲突消解 (Conflict Resolution - Graph Coloring)
使用 **图着色 (Graph Coloring)** 算法（具体实现为 **DSatur** 算法）来寻找可行解。
*   **建模**:
    *   **节点**: 每一个灵活任务。
    *   **颜色**: 可用的时间槽。
    *   **边 (约束)**: 如果两个任务不能同时进行（个人通常是单线程的），它们之间存在冲突边。
*   **作用**: 快速筛选出满足硬性约束（如截止日期、不重叠）的候选时间槽分配方案。

#### 1.5 偏好优化 (Preference Optimization - Bipartite Matching)
在确保可行性的基础上，系统使用 **二分图最大权匹配 (Bipartite Maximum Weight Matching / Hungarian Algorithm)** 寻找全局最优的时间槽分配。

*   **目标**: 最大化任务与时间槽的匹配度。
*   **评分维度**:
    1.  **精力匹配 (Energy Match)**:
        *   **高精力时段**: 系统根据历史数据分析出用户在**一周内每一天**的高精力时段（例如：周一上午、周五下午）。
        *   **匹配逻辑**: 高精力任务匹配高精力时段得分最高；错配则扣分。
    2.  **碎片化管理 (Fragmentation)**:
        *   使用 \FragmentationUtils\ 检测时间槽是否处于“碎片”状态（即紧邻忙碌时段）。
        *   **填补空隙**: 优先选择碎片时间槽，以减少日程中的零散空隙。
    3.  **任务关联性 (Task Connections / Community)**:
        *   使用 **社区发现 (Community Detection)** 算法识别任务群组。
        *   尝试将同一社区的任务安排在相近的时间段（如同一社区的任务都倾向于上午），以减少上下文切换。
    4.  **优先级 (Priority)**: 高优先级任务获得更高的权重。

*   **算法执行**: 构建权重矩阵 \{ij}\$ (任务 \\$ 在时间槽 \\$ 的得分)，运行匈牙利算法寻找总分最高的匹配方案。

#### 1.6 结果回写
算法输出每个灵活任务的建议时间段（Start, End），并根据“父子任务”模型生成一个新的**子任务**作为建议安排。
*   **父任务**: 原始的 DDL 任务，保持不变（作为需求/模板）。
*   **子任务**: 新生成的任务，具有新的 ID，\parentTaskId\ 指向父任务，\isFixed=true\，且时间被设置为算法建议的时间段。

## 2. 团队任务调度 (Team Schedule)

团队任务调度的目标是找到一个最佳的会议/共同任务时间，使得关键成员能够参加，同时最大化团队偏好并最小化对个人日程的干扰。

### 核心流程

整个调度过程由 \AlgorithmService.scheduleTeamTasks\ 和 \LinearProgramming\ 服务编排。

#### 2.1 成员忙闲提取 (Availability Extraction)
系统遍历所有参与成员的任务列表，提取“忙碌时间段” (Busy Slots)。
*   **判定标准**: 任何标记为 \isFixed\ 的任务，或者具有明确时间跨度 (\start < end\) 的任务，都被视为该成员在该时段不可用。

#### 2.2 候选时间槽生成 (Candidate Slot Generation)
根据会议要求（时长、最早开始时间、最晚结束时间），系统生成一系列候选的会议时间段。

#### 2.3 优化评估 (Heuristic Search / Linear Programming)
系统对每一个候选时间槽进行评分评估，寻找全局最优解。虽然模块名为 \LinearProgramming\，实际实现采用了基于权重的启发式搜索（Heuristic Search with Weights），这在离散时间槽场景下更高效。

对于每个候选槽，计算以下指标：

1.  **可行性 (Validity)**:
    *   检查所有 **必须参与者 (Required Participants)** 是否在该时段空闲。
2.  **偏好得分 (Preference Score)**:
    *   汇总所有能参加成员对该时间段的偏好值。
3.  **调整成本 (Adjustment Cost)**:
    *   计算安排在该时段会造成的“冲突成本”（如可选参与者缺席）。
4.  **目标函数 (Objective Function)**:
    \$\$ Score = (TotalPreference \\times W_{pref}) - (TotalCost \\times W_{cost}) \$\$
    *   系统选择 \\$ 最高的候选槽作为最终建议。

## 3. 辅助算法与架构决策

### 3.1 社区发现与高精力时段 (Community Detection & High Energy Patterns)

*   **高精力时段发现**:
    *   **数据源**: 用户的历史任务记录。
    *   **粒度**: **按周几 (Day of Week)** 分组分析。这意味着系统能区分“周一综合症”和“周五狂欢”，为每一天生成独立的精力模式。
    *   **算法**: 
        1.  将每一天的小时（0-23）作为节点。
        2.  如果两个小时在同一天的历史记录中频繁出现任务，则建立连接。
        3.  运行社区发现算法，识别出紧密连接的时间段群组（如 9:00-11:00）。
    *   **存储**: 结果以 \Record<number, Period[]>\ 格式存储，Key 为 0-6 (周日-周六)。

### 3.2 碎片化检测 (Fragmentation Detection)

*   **独立模块**: 逻辑封装在 \FragmentationUtils\ 中。
*   **原理**: 检查一个空闲时间槽的前后是否紧邻“忙碌”状态（固定事件或边界）。
*   **策略**: 调度算法倾向于优先填充这些碎片时间，以避免将大块连续的空闲时间打散，从而保留整块时间用于深度工作或休息。
